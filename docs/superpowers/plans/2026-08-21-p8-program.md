# P8 Safe Publishing & GEO Distribution Program Execution Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. This is the orchestration plan for the three approved implementation plans; execute P8-A → P8-B → P8-C continuously and then Task 27 final release.

**Goal:** Deliver the complete approved P8 program—safe primary publishing, multi-channel distribution, Community GEO, and entity/knowledge-graph suggestions—as one auditable integration program, with exact-head release gates at each milestone and a final exact-head merge to `main`.

**Architecture:** The common integration branch is `docs/p8-safe-site-mutation-design`, which already contains the approved design and implementation plans. Implementation tasks use isolated task branches based on the current integration head and merge back only after the task's RED/GREEN verification. P8-A, P8-B, and P8-C each receive a milestone exact-head CI gate. Passing a milestone gate is permission to continue to the next approved phase; it is not a request to reopen architecture. Only the final P8 integration PR targets `main`.

## Locked Program Rules

- Execute all approved tasks 1–27. Do not stop after P8-A or P8-B to ask whether to continue; stop only for an actual blocker, safety boundary, failed gate needing diagnosis, or a material design contradiction.
- Every implementation task follows TDD: intended RED → minimal GREEN → focused regression → task commit.
- Use isolated task branches; recommended names:
  - `feat/p8a-task-01-...` through `feat/p8a-task-15-...`
  - `feat/p8b-task-16-...` through `feat/p8b-task-21-...`
  - `feat/p8c-task-22-...` through `feat/p8c-task-26-...`
  - `feat/p8-task-27-release-gate`
- Each task PR bases onto `docs/p8-safe-site-mutation-design`, not `main`, until Task 27.
- Never merge a task PR whose intended tests or required CI are red. Use exact head SHA for merge authorization.
- At P8-A/P8-B/P8-C milestone heads, require all three GitHub CI jobs: `verify`, Chromium `e2e`, `production-audit`.
- No live DeepSeek, Google, external distribution, community, encyclopedia, or production Git write credential is required by CI.
- The P8 Git mutation feature itself is tested with injected/fake transports in CI; test execution must never mutate the real `xingshantang.org` repository.
- `xingshantang.org` primary production repository must be explicitly configured/authorized during real operator setup; the implementation cannot infer write permission from the domain name.
- HIGH-risk site mutations, auto merge, auto deployment, autonomous rollback, automatic community participation, and encyclopedia publishing remain out of scope even at P8 COMPLETE.
- P9 autonomous orchestration is not implemented in this program.

## Milestone Gate Procedure

At the final exact head of P8-A, P8-B, and P8-C:

1. Run/fetch exact-head CI for the integration branch.
2. Confirm `verify`, Chromium `e2e`, and `production-audit` all succeed on that exact SHA.
3. Confirm no unresolved blocking review threads/comments on the milestone PR.
4. Record exact head SHA and workflow run in the milestone PR/release notes.
5. Continue immediately to the next approved plan.

A prior green SHA is not evidence for a newer head. Any release-documentation commit after a green gate requires a fresh exact-head CI run.
